# Отчёт об аудите и готовности — Greenol

Дата: 2026-11-19. Сайт: https://sosukii.github.io/greenol-shop/ · Админка: https://sosukii.github.io/greenol-shop/admin/login

## Вердикт: **NO-GO для боевого запуска**, GO для демонстрации и приёмки заказчиком

Витрина, каталог, корзина, оформление, SEO и админка работают и проверены. Но запуск продаж блокируют вещи,
которые нельзя сделать без заказчика или без платного хостинга (раздел «Блокеры»).

### Дефекты, найденные тестами уже при доработке (и исправленные)
- `/catalog` не попадал в prerender (route с необязательным параметром) — 404 на GitHub Pages.
- Скачок заголовков H1→H3 на страницах каталога (нужен H2).
- Product JSON-LD без `image` у товара без фото (Google требует) — подставляется изображение по умолчанию.
- `markPaidManually` бросал исключение синхронно вместо rejected promise.
- В данных источника 2 товара с ценой 0 → заведена модель «цена по запросу» (нельзя купить, есть «Запросить цену» → заявка).
- Логотип отображался в натуральном размере из-за моего глобального CSS (перебивал Tailwind layers).
- Переполнение шапки панели каталога на 320 px; кликабельные зоны 17–20 px (хлебные крошки, футер, таблицы админки).
- Динамические адреса `/order/<id>`, `/admin/orders/<id>` на статическом хостинге давали 404-документ → заменены на `/order?id=`, `/admin/order?id=`.
- Lighthouse a11y: роли listitem на кнопках, контраст slate-400/500, ссылка в тексте без подчёркивания.

## 3. Страницы и viewport
Проверены: главная, каталог, 3 категории (включая вложенную и без подкатегорий), 3 карточки (с фасовками, длинным описанием, «цена по запросу»), поиск (результат/пусто), корзина (пусто/с товарами), оформление (пусто/форма/ошибки), заказ (ожидание/успех/отмена/ошибка/принят/не найден), О магазине, Доставка и оплата, Контакты, 404, вход в админку, заказы, карточка заказа, лиды, аналитика.
Viewport: 320–1600 px (см. выше). **Визуально (глазами) я просмотрел лишь часть скриншотов** (главная и товар на 390, каталог на 1280); остальные проверены автоматически по геометрии, а не оценены на красоту — рекомендую дизайнерский просмотр.

Честные оговорки: «до» — почти пустая оболочка с 4 иконками-заглушками (59 КБ), поэтому её оценка не говорит о качестве; «после» — реальный каталог с фото (165–373 КБ). Меры: prerender, route-level code splitting (админка — отдельные чанки), системные шрифты (0 КБ, нет CLS), WebP 320/640/960 с srcset/sizes, `width/height`, lazy, `fetchpriority` для LCP, долгий кэш `assets/` и `img/` (на GitHub Pages заголовки задать нельзя — кэш по умолчанию 10 минут).

## 5. SEO-аудит
Проверяется на статическом HTML (как видит робот без JS), все страницы: `lang=ru`; `header/nav/main/footer`; ровно один осмысленный H1 и иерархия без скачков (тест на каждой странице); title ≤ 90 и description 40–320 знаков; canonical; Open Graph; `alt` у всех изображений; JSON-LD: Organization, WebSite (SearchAction), BreadcrumbList, Product + Offer/несколько Offer (цена, RUB, InStock/BackOrder), у товара без цены Offer не выводится; `noindex` у корзины, оформления, заказа, админки, 404 и у страниц с поиском/фильтрами/пагинацией (canonical без параметров); `robots.txt` (+Sitemap), `sitemap.xml` (58 URL, без закрытых страниц); URL ЧПУ (`/product/<slug>`, `/catalog/<slug>`); нет битых ссылок (все URL sitemap и ссылки главной → 200).
**SPA vs prerender:** выбран SSG (каждая страница — готовый HTML) — индексируется без выполнения JS. Hash-режим убран.
Оговорки: canonical/sitemap используют адрес `*.github.io` — при переносе на домен задать `VITE_SITE_URL` и пересобрать; Rich Results Test Google/Yandex Вебмастер я не запускал (нужен доступ); `Offer.availability=BackOrder` для «Под заказ» — интерпретация, согласовать.

## 6. Audit оформления заказа (checkout)
Пройдено: главная → поиск/каталог → категория → товар → корзина → изменение количества → оформление → доставка → расчёт → оплата → возврат → заказ в админке.
Проверено: двойной клик (1 заказ), перезагрузка страницы оформления (тот же ключ), валидация (имя/телефон/город/адрес/email/согласие, фокус на первой ошибке), смена города/службы пересчитывает доставку, оплата успех/ошибка/отмена/повтор, повторная оплата оплаченного заказа невозможна (на уровне ядра), заказ сохраняется после неудачной оплаты, наличные/счёт без платёжной страницы, недоступный товар («цена по запросу» не добавляется; сервер отклоняет неизвестный артикул и товар без цены), подмена цены в запросе игнорируется (сервер считает по каталогу), количество 1–99.
Не проверено на реальных системах: ошибки API банка/СДЭК (их нет), webhook реального банка — только подпись HMAC и логика в тестах.

## 7. Audit админки (глазами владельца)
Вход (неверный пароль → отказ; прямой переход → редирект на логин) → список заказов (поиск по номеру/имени/телефону, фильтры статуса заказа и оплаты, сортировка, пагинация 10, CSV) → карточка (состав, покупатель, доставка, суммы, способ и статус оплаты, история) → смена статуса → ручная «оплачено» (обязательна причина, пишется в аудит) → лиды (статусы, UTM) → аналитика (заказы/выручка/средний чек/по дням/по статусам/топ товаров; блок Метрики честно показывает «не подключено»). Тестовый заказ с сайта появляется в админке с корректными данными (e2e + живой смоук).
**Ключевое ограничение:** на GitHub Pages админка работает в **локальном режиме** — заказы хранятся в браузере покупателя, а логин проверяется в браузере. Заказ, оформленный на другом устройстве, владелец **не увидит**; пароль не защищает данные. Настоящий режим — `server/` (httpOnly-cookie, rate limit, подпись webhook), протестирован, но не развёрнут.
Не реализованы роли (только владелец; архитектура `role` в токене заложена), печать документов, редактирование состава заказа.

## 8. Что не исправлено / открыто (блокеры и риски)
**Блокеры запуска:**
1. Бэкенд не развёрнут (нужен хостинг: Node + БД; платный сервис — нужно ваше подтверждение), без него реальные заказы не попадают владельцу.
2. Оплата — песочница: банк/провайдер и ключи не выбраны; webhook реального банка не проверялся.
3. Доставка СДЭК/Ozon — **условная тарифная таблица** (`src/config/site.ts`), реальные API, договоры, вес/габариты неизвестны. Везде подписано «ориентировочно».
4. Юридические тексты: политика конфиденциальности и согласие (чекбокс есть, ссылки на документ нет). Страницы «Возврат» и «Гарантии» на старом сайте содержат заглушку «text here» — не перенесены.
5. Не заданы: ID Метрики (счётчик не подключён, цели реализованы и описаны в `docs/ANALYTICS.md`), ссылки MAX/Telegram/WhatsApp, уведомления о заказах (email/Telegram), роли админки.

**Вопросы по данным (взято с действующего сайта как есть):**
- Структура категорий странная (чехлы и шинные пакеты лежат в «Автомасла → Защитные материалы»); ТОТЕК-масла частично в «Автохимии».
- 2 товара с ценой 0 (Реаниматор 5 л, трансмиссионное масло Totek 4 л) → «Цена по запросу»; 1 товар без фото; описания — «сплошной текст» с опечатками; в названиях упаковок не везде указано количество (например, цена 18 000 ₽ за «450 мл» — это упаковка 20 шт).
- Наличие в источнике бинарное; «OutOfStock» показано как «Под заказ». Вес/габариты не импортированы (единицы несогласованы).
- Блок способов оплаты старого сайта (квитанция Сбербанка, Яндекс.Деньги/WebMoney) не перенесён — устарел и не поддерживается новым оформлением. Банковские реквизиты (счёт, БИК) с контактов **намеренно не опубликованы** (ИП, ИНН, ОГРНИП — оставлены).
- Отзывы с источника не импортированы (нужна проверка подлинности); права на фото и тексты принадлежат заказчику — подтвердить.
- Цвет бренда: логотип Greenol зелёный, CTA — синий по ТЗ («синий продающий»). Подтвердить с дизайнером.

## 9. Финальный аудит в пяти ролях
**Product Manager.** Полный пользовательский путь есть и работает; контент реальный; бизнес-процесс после заказа (уведомление менеджера, подтверждение доставки, оплата по счёту) не автоматизирован. Риски: оплата/доставка/юристы/хостинг. Готовность к запуску: ~60% (технически витрина готова, операционно — нет).
**QA.** 125 автоматических проверок зелёные; edge-cases (двойной клик, reload, недоступный товар, плохие данные, отмена оплаты) покрыты. Не покрыто: кроссбраузерность, устройства, нагрузка, реальные платежи, localStorage-ограничения приватных режимов (код обёрнут в try/catch, но не тестировался).
**UI/UX.** Единая система (UI-кит, `classes`), mobile-first, нижняя навигация, фильтры в модалке, анимации (появление, hover, тост и «bump» при добавлении, `prefers-reduced-motion`). Замечания: страницы сильно отличаются по плотности (главная насыщеннее); карточки товаров с разной пропорцией фото в квадратной рамке (`object-contain`) — вид «воздушный»; нужен дизайнерский просмотр, у категорий нет иллюстраций.
**Senior Developer.** Общее ядро для сервера и клиента (единые правила), адаптеры API/каталога, строгий TS, тесты. Долг: JSON-файл вместо БД и in-memory rate-limit (один инстанс); клиентская «авторизация» локального режима — только демо; каталог собирается скриптом из HTML старого сайта (хрупко); отсутствует CI-запуск e2e (нужен ADMIN_PASSWORD secret); нет мониторинга ошибок и бэкапов.
**Обычный пользователь.** Купить товар без подсказок можно: понятные кнопки, ошибки рядом с полями, итог с доставкой виден до оплаты. Раздражители: стоимость доставки «ориентировочная» и менеджер подтверждает её позже; у части товаров «Под заказ» без срока; нет юридических документов рядом с чекбоксом.
